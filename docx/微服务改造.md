---
  一、先搞懂：你现在的架构长什么样

  你现在是一个单体应用，所有东西跑在一个进程里：
                          ├── handler/system/role/...              --> logic/system/role/...
                         浏览器 --HTTP请求--> plating.go（888第 8 章口，一个进程）
                              |
                              ├── handler/auth/login_handler.go        --> logic/auth/login_logic.go
                              ├── handler/system/user/list_user_handler.go --> logic/system/user/list_user_logic.go
                         └── ...所有功能都在这一个进程里
                          |
                          └── 直接操作 MySQL / Redis / Casbin

  关键特征： handler 直接 new 一个 logic，logic 直接通过 svcCtx.SysUserModel 操作数据库。所有代码在同一个
  go-zero-admin 模块里，编译出一个二进制文件。

---
  二、微服务架构长什么样

  微服务就是把一个大程序拆成几个小程序，各自独立运行，通过网络互相调用：

  浏览器 --HTTP请求--> Gateway（888第 8 章口，进程A）
                          |
                    gRPC调用（走网络，不是函数调用！）
                          |
                ┌─────────┴──────────┐
                |                     |
           sys-rpc                plating-rpc
          （9100端口，进程B）      （9200端口，进程C）
                |                     |
           操作 sys_* 表          操作 plate_* 表

  三个独立程序，各自有自己的 main 函数，各自启动，各自监听不同端口。

---
  三、什么是 Gateway？为什么需要它？

  Gateway 就是你现在的 HTTP 层"瘦身版"

  你现在的 plating.go 启动一个 HTTP 服务器，浏览器直接请求它。微服务化后，浏览器还是请求同一个 HTTP 地址，但这个
  HTTP 服务器不再自己干活了——它变成了一个"传话筒"：

  **现在（单体）的 handler：**

      // handler 直接 new logic，logic 直接查数据库
      func ListUserHandler(svcCtx *svc.ServiceContext) http.HandlerFunc {
          return func(w http.ResponseWriter, r *http.Request) {
              var req types.ListUserReq
              httpx.Parse(r, &req)
              // 直接调用本地 logic
              l := user.NewListUserLogic(r.Context(), svcCtx)
              resp, err := l.ListUser(&req)
              // ...
      }
  }

  **微服务化后的 Gateway handler：**

      // handler 不再 new logic，而是调用远程的 sys-rpc 服务
      func ListUserHandler(svcCtx *svc.ServiceContext) http.HandlerFunc {
          return func(w http.ResponseWriter, r *http.Request) {
              var req types.ListUserReq
              httpx.Parse(r, &req)
              // 通过 gRPC 调用 sys-rpc 服务（走网络！）
              resp, err := svcCtx.SysRpc.ListUser(r.Context(), &sys.ListUserReq{
                  Page:     req.Page,
                  PageSize: req.PageSize,
                  Keyword:  req.Keyword,
                  Status:   int64(req.Status),
              })
              // ...
      }
  }

####   Gateway 的职责

  ┌─────────────────┬───────────────────────────────────────────────────────────────┐
  │      职责                                 │                             说明                              │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ 接收 HTTP 请求  │ 浏览器/前端只跟 Gateway 打交道，地址不变                      │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ JWT 鉴权        │ 验证 token（你现在的 AuthMiddleware 留在这里）                │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ Casbin 权限校验 │ 检查"这个用户能不能访问这个接口"（CasbinMiddleware 留在这里） │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ 参数转换        │ 把 HTTP 请求参数转成 gRPC 请求参数                            │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ 转发请求        │ 调用对应的 RPC 服务                                           │
  ├─────────────────┼───────────────────────────────────────────────────────────────┤
  │ 返回响应        │ 把 RPC 返回结果转成 JSON 返回给浏览器                         │
  └─────────────────┴───────────────────────────────────────────────────────────────┘

  一句话：Gateway = 你现在的 handler 层 + middleware 层，但把 logic 层的代码搬走了。

  Gateway 调用什么？

  浏览器请求 /api/system/user   --> Gateway --> gRPC调用 --> sys-rpc（处理用户管理）
  浏览器请求 /api/system/role   --> Gateway --> gRPC调用 --> sys-rpc（处理角色管理）
  浏览器请求 /api/auth/login    --> Gateway --> gRPC调用 --> sys-rpc（处理登录认证）
  浏览器请求 /api/plating/tank  --> Gateway --> gRPC调用 --> plating-rpc（处理槽液业务）

  Gateway 根据 URL 前缀决定调用哪个 RPC 服务。/api/system/* 和 /api/auth/* 走 sys-rpc，/api/plating/* 走
  plating-rpc。

---
  四、什么是 gRPC？和你现在的 HTTP 有什么区别？

  类比理解

  你现在的方式：
  前端 --JSON（HTTP）--> handler --Go函数调用--> logic --Go函数调用--> model --> MySQL

  微服务的方式：
  前端 --JSON（HTTP）--> Gateway --Protobuf（gRPC）--> sys-rpc --Go函数调用--> model --> MySQL

  gRPC 就是"微服务之间的通信协议"，类似 HTTP，但：
  - HTTP 传 JSON（文本），gRPC 传 Protobuf（二进制），更快
  - HTTP 是浏览器能理解的，gRPC 是程序之间用的
  - go-zero 对 gRPC 有完整支持，跟你写 HTTP API 一样简单

  Protobuf 是什么？

  你现在用 .api 文件定义 HTTP 接口，微服务用 .proto 文件定义 gRPC 接口。它们是对应的：

  你现在的 user.api（定义 HTTP 接口）：

```json
 type ListUserReq {
      Page     int    `form:"page,default=1"`
      PageSize int    `form:"pageSize,default=20"`
      Keyword  string `form:"keyword,optional"`
      Status   int    `form:"status,optional"`
  }

  type ListUserResp {
      Total int64      `json:"total"`
      List  []UserItem `json:"list"`
  }

  service plating-api {
      @handler ListUserHandler
      get /user (ListUserReq) returns (ListUserResp)
  }
```

  对应的 sys.proto（定义 gRPC 接口）：

```
syntax = "proto3";

package sys;

option go_package = "./sys";

// 请求消息（对应你的 ListUserReq）
message ListUserReq {
    int64  page      = 1;
    int64  pageSize  = 2;
    string keyword   = 3;
    int64  status    = 4;
}

// 用户信息（对应你的 UserItem）
message UserItem {
    int64    id        = 1;
    string   username  = 2;
    string   nickname  = 3;
    string   email     = 4;
    string   phone     = 5;
    int64    status    = 6;
    string   avatar    = 7;
    string   remark    = 8;
    repeated string roles = 9;   // repeated = 数组
    string   createdAt = 10;
    string   updatedAt = 11;
}

// 响应消息（对应你的 ListUserResp）
message ListUserResp {
    int64           total = 1;
    repeated UserItem list = 2;
}
```

```
  // 服务定义（对应你 .api 里的 service 块）
  service SysService {
    rpc ListUser(ListUserReq) returns (ListUserResp);
    rpc CreateUser(CreateUserReq) returns (CommonResp);
    rpc UpdateUser(UpdateUserReq) returns (CommonResp);
    rpc DeleteUser(DeleteUserReq) returns (CommonResp);
    // ...其他所有系统管理方法
    rpc Login(LoginReq) returns (LoginResp);
    rpc GetMenuTree(GetMenuTreeReq) returns (GetMenuTreeResp);
    // ...
  }
```

  写完 .proto 文件后，用 goctl 一键生成代码：
  goctl rpc protoc sys.proto --go_out=. --go-grpc_out=. --zrpc_out=.

  这条命令会自动生成：
  - internal/server/ -- gRPC server 骨架（类似你现在的 handler）
  - internal/logic/ -- 业务逻辑骨架（类似你现在的 logic，需要你填充）
  - internal/svc/ -- ServiceContext（类似你现在的 svc）
  - internal/config/ -- 配置结构体
  - sysclient/ -- 客户端代码（Gateway 用这个来调用 sys-rpc）
  - sys.go -- 入口文件（类似你的 plating.go）

  第3 章步：迁移 logic 代码到 sys-rpc

  这是最关键的一步。 你现在的 logic 代码几乎可以原封不动搬过去。

  对比一下：

  现在的 list_user_logic.go（在单体项目中）：
  package user

  import (
      "go-zero-admin/internal/svc"
      "go-zero-admin/internal/types"

  type ListUserLogic struct {
      ctx    context.Context
      svcCtx *svc.ServiceContext   // <-- 单体的 ServiceContext

  搬到 sys-rpc 后的 list_user_logic.go：

  import (
      "go-zero-admin/service/sys/rpc/internal/svc"      // <-- sys-rpc 自己的 ServiceContext
      "go-zero-admin/service/sys/rpc/sys"                // <-- protobuf 生成的类型

  type ListUserLogic struct {
      ctx    context.Context
      svcCtx *svc.ServiceContext   // <-- sys-rpc 的 ServiceContext（也持有 SysUserModel）

  3. 业务逻辑代码不变！你的 SysUserModel.List() 调用完全一样

  第6 章步：创建 Gateway

  Gateway 就是新建一个 go-zero HTTP 服务，但它不直接查数据库，而是调用 RPC。

  Gateway 的 ServiceContext：
  type ServiceContext struct {
      Config config.Config

      // 不再持有任何 Model！不直接操作数据库
      // 而是持有 RPC 客户端
      SysRpc      sysclient.SysService          // sys-rpc 的客户端
      PlatingRpc  platingclient.PlatingService   // plating-rpc 的客户端
    
      // 中间件还在 Gateway
      AuthMiddleware   func(...)
      CasbinMiddleware func(...)
  }

  Gateway 的配置文件 gateway.yaml：
  Name: gateway
  Host: 0.0.0.0
  Port: 8888                # HTTP 端口（跟你现在一样，前端无感知）
  Timeout: 30000

  Auth:
    AccessSecret: "your-secret"
    AccessExpire: 1200

  # 告诉 Gateway 去 etcd 找 sys-rpc 和 plating-rpc
  SysRpc:
    Etcd:
      Hosts:
        - 127.0.0.1:2379
      Key: sys.rpc           # 跟 sys.yaml 里的 Key 对应

  PlatingRpc:
    Etcd:
      Hosts:
        - 127.0.0.1:2379
      Key: plating.rpc

  Gateway 怎么知道 sys-rpc 在哪？
  1. sys-rpc 启动时，向 etcd 注册："我叫 sys.rpc，我在 192.168.1.100:9100"
  2. Gateway 启动时，问 etcd："sys.rpc 在哪？"
  3. etcd 告诉 Gateway："在 192.168.1.100:9100"
  4. Gateway 就知道往哪发 gRPC 请求了

  这就是服务注册发现，你不用手动写 IP 地址。

  Gateway 的 handler（以列表用户为例）：
  func ListUserHandler(svcCtx *svc.ServiceContext) http.HandlerFunc {
      return func(w http.ResponseWriter, r *http.Request) {
          var req types.ListUserReq
          httpx.Parse(r, &req)

          // 核心变化：不再 new logic，而是调 RPC
          resp, err := svcCtx.SysRpc.ListUser(r.Context(), &sys.ListUserReq{
              Page:     int64(req.Page),
              PageSize: int64(req.PageSize),
              Keyword:  req.Keyword,
              Status:   int64(req.Status),
          })
          if err != nil {
              response.FailInternal(w, r)
              return
          }
    
          httpx.OkJsonCtx(r.Context(), w, resp)
      }
  }

  七、微服务之间的调用关系总览

  请求完整链路示例：前端点击"创建生产事件"按钮

  1. 前端 POST /api/plating/production  (带 JWT Token)
         |
  2. Gateway 收到请求
     ├── AuthMiddleware 验证 JWT Token --> 提取 userId
     ├── CasbinMiddleware 检查权限 --> 调用 sys-rpc.CheckPermission() 验证
     └── handler 转发请求 --> 调用 plating-rpc.CreateProductionEvent()
         |
  3. plating-rpc 收到 gRPC 请求
     ├── 需要用户昵称？ --> 调用 sys-rpc.GetUserById() 获取
     ├── 正常业务逻辑 --> 操作 plate_production_events 表
     └── 返回结果给 Gateway
         |
  4. Gateway 把结果转成 JSON 返回给前端

  调用关系汇总：

  Gateway --> sys-rpc      （所有 /api/system/* 和 /api/auth/* 请求）
  Gateway --> plating-rpc  （所有 /api/plating/* 请求）
  Gateway --> sys-rpc      （CasbinMiddleware 做权限校验时）
  plating-rpc --> sys-rpc  （业务逻辑需要用户/角色信息时，可选）
