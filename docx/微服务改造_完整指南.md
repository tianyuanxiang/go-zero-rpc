## 第 0 章  改造前你必须先理解的事

### 0.1 为什么要改造？说人话

| 现状（单体）                               | 改造后（微服务）
                                 |
| ------------------------------------------ | ------------------------------------------------- |
| 一个进程，一个二进制，HTTP 直接接数据库    | 多个进程，Gateway 接 HTTP，sys-rpc 接数据库       |
| 加新业务（如电镀业务）只能往同一个项目塞   | 加新业务 = 新建一个 RPC 服务，独立部署、独立扩缩容 |
| 系统管理逻辑无法被其他项目复用
            | sys-rpc 可作为基础服务被任何业务服务以 gRPC 调用  |

一句话：**现在你写的 通用系统管理"代码会变成一个 基础应 ——任何新业务项目，启动一个 plating-rpc / order-rpc / xxx-rpc，通过 gRPC 调 sys-rpc 拿用户、查权限、记操作日志，不用再 copy 代码。**

### 0.2 改造心智准备（最重要）

- **改造 ≠ 重写**。你 90% 的 logic 代码会原封不动搬过去，只改 import 路径和类型名。
- **不要一次性全部迁定
*。先过 1 个接口（比如 Login），跑通完整链路（前端 → Gateway → sys-rpc → MySQL → 返回），再批量迁其他的。
- **不要一开始就追求完美**。先让流程跑起来，再表（Casbin、再表"OperLog、再补文件上传。
- **保留原项目能路**。新项目放在 `D:\GoProject\project_new\go-zero-admin\`（新目录），改造期间老项目 `go-zero-rpc\` 不要动。

### 0.3 一些管听起来很现在的概念其实很简单

- **gRPC 调用** = 函数调用，只是这个函数实现在另一个进程里，参数通过网络传过去。你写 `svcCtx.SysRpc.Login(ctx, &sys.LoginReq{...})` 跟你现在写 `svcCtx.SysUserModel.FindOneByUsername(ctx, name)` 一样自然。
- **Protobuf** = 跨进程版的 Go struct。`.proto` 文件就是 struct 定义文件，`goctl` 帮你把它编译成各语言可用的代码。
- **etcd** = 一个微型数据库，专门用来存"哪个服务在哪个 IP 端口"。你只需要 `docker run` 一下，剩下都是 go-zero 自动跟它打交道。

## 第 2 章  核心概念扫盲（不懂这些就别动手）

### 2.1 gRPC vs HTTP

| 项目         | HTTP                       | gRPC                                   |
| ------------ | -------------------------- | -------------------------------------- |
| 数据格式     | JSON（文本）               | Protobuf（二进制，更小更快）            |
| 接口定义     | `.api` 文件                | `.proto` 文件                          |
| 客户端写法   | `httpx.Parse(r, &req)`     | `client.Method(ctx, &Req{...})`        |
| 用途         | 浏览器 → 服务器             | 服务 → 服务（内部通信）
               |

**对你而言关键的是**：写 `.proto` 文件 + `goctl rpc protoc` 生成代码，剩下跟写 go-zero HTTP 几乎一样。

### 2.2 Protobuf 文件长什么样

对比你现在的 `.api`：

```go
// user.api
type ListUserReq {
    Page     int    `form:"page,default=1"`
    PageSize int    `form:"pageSize,default=20"`
    Keyword  string `form:"keyword,optional"`
    Status   *int   `form:"status,optional"`
}
```

对应的 `.proto`）

```protobuf
// sys.proto
message ListUserReq {
    int64  page     = 1;     // 数字 1/2/3 是字段编号（不是值），传输时按编号编码     int64  pageSize = 2;
    string keyword  = 3;
    int64  status   = 4;     // 注意：proto3 没有指针，改用 0 表示"未设置"
    bool   hasStatus = 5;    // 如果 status=0 也是一种过滤值，用一个额外字段标记是否传入
}
```

**关键差异（必须记住）**：

1. proto3 **没有原生的指针（可选语义）**。你 `.api` 里的 `*int` 在 proto 里要么用 0 表示空，要么加一个 `bool hasXxx` 标记，要么用 `optional`（proto3 后期版本支持，但生成的 Go 代码用法更复杂）。**推荐方案**：用 0/空字符串表示未传，业务上能区分的字段（如 status 的 0 是有效值）就加 `bool hasStatus`。
2. proto 字段名风格是 `snake_case`，但 protoc-gen-go 会自动转成 Go 的 `CamelCase`。
3. 字段编号 1-15 用 1 字节编码，16+ 用 2 字节；**高频字段编号尽量小**。

### 2.3 etcd 是什么？
把它想象成一个 电话簿：

- sys-rpc 启动时打电话给 etcd："喂，我叫 sys.rpc，我在 192.168.1.10:9100"
- gateway 启动时打电话给 etcd："sys.rpc 在哪？"

- etcd 答："在 192.168.1.10:9100"
- gateway 拿到地址后跟 sys-rpc 建 gRPC 连接

**为什么不写死 IP：** 因为 sys-rpc 可以部署多个实例（负载均衡），etcd 会把所有实例的地址都告诉 gateway，gateway 用 round-robin 轮询调用。

### 2.4 goctl 是什么？
它是 go-zero 的 代码生成器）。你写 `.proto`，它帮你生成：

```
sys-rpc/
├── etc/sys.yaml                    <-- 配置文件骨架
├── internal/
│   ├── config/config.go            <-- 配置 struct
│   ├── server/sys_server.go        <-- gRPC 服务端入口（你不用改）
│   ├── svc/service_context.go      <-- ServiceContext（你要改这个）
│   └── logic/                      <-- 业务逻辑文件（你要填这里） │       ├── login_logic.go
│       ├── list_user_logic.go
│       └── ...
├── sys/                            <-- protobuf 生成的 Go 类型
│   ├── sys.pb.go
│   └── sys_grpc.pb.go
├── sysclient/                      <-- 给别人调用的客户端代码 │   └── sys.go
└── sys.go                          <-- main 入口
```

**你只需要改 4 个地新**：`.proto` 文件、`service_context.go`、`logic/*.go`、`etc/*.yaml`。其余都是自动生成。

### 5.3 第三步：初始化 common 模块（最关键，最容易卡住）

> **新手必读：什么是 `go mod init`？什么是 `go.mod`：**
>
> Go 用户模块"管理一个或多个 Go 包。一个模块对应一个 `go.mod` 文件（由 `go mod init <模块名/` 命令产生）。
> `go.mod` 文件的作用是声明）
> - 这个模块叫什么名字（其他代码 import 时用这个名字）
> - 用什么版本的 Go
> - 依赖了哪些第三方库（require 段）
>
> **没有 `go.mod`，IDE 就不认这个目录是 Go 模块**，所以 import 全部报红——这就是您遇到的"Cannot resolve symbol"的根本原因。

#### 5.3.1 命令

```bash
cd D:/GoProject/project_new/go-zero-admin/common

go mod init go-zero-admin/common
```

### 5.6 第六步：解决 IDE 报红——`go mod tidy` 下载依赖

> **关键知识点：为什么会把 "Cannot resolve symbol 'golang-jwt'"：**
>
> 因为：
> 1. 您新建的 `common/go.mod` 是空的，没有声明任何 `require`
> 2. `jwt.go` 重新`import "github.com/golang-jwt/jwt/v5"` 这个第三方库，本地根本没下载
> 3. IDE 顺着 `go.mod` 找不到这个包，于是标线
>
> 解决办法只有一行命令：`go mod tidy`。它会自动扫描所有 `.go` 文件的 import，把缺失的依赖写入 `go.mod` 并下载到本地缓存。

#### 5.6.1 命令

```bash
cd D:/GoProject/project_new/go-zero-admin/common

go mod tidy
```

#### 5.6.2 这条命令做什么？
按顺序执行四件事：

1. 扫描 `common/` 下所有 `.go` 文件，收集成import 列表
2. 对每个 import）
   - 标准库（如 `fmt`, `errors`）→ 跳过
   - 已声明且使用的依赖注→ 保留
   - 未声明但被使用的 → 加到 `go.mod` 的 `require` 段，并从网上下载
   - 已声明但没被使用的 → 从 `go.mod` 删除
3. 把所有依赖的精确版本和校验码写入 `go.sum`
4. 把第三方库源码下载到 `$GOPATH/pkg/mod/`（全局缓存，不会塞到您项目里）

`common/go.mod` 变成：

```

```


#### 5.6.6 `go mod tidy` 报错怎么办？

> 3. 生成 client 包（给别的服务调用本服务用的）

#### 6.3.1 命令

```bash

  --go-grpc_out=. \
  --zrpc_out=. \
```

> Windows cmd 不支持 `\` 续行，所有命令写一行：
> `goctl rpc protoc pb/sys.proto --go_out=. --go-grpc_out=. --zrpc_out=. -m`

| 参数               | 作用                                                 |
| ------------------ | ---------------------------------------------------- |
| `pb/sys.proto`     | 输入文件                                             |

               |
| `--zrpc_out=.`     | 生成 go-zero 风格的 main+config+svc+logic+server 骨架 |
| `-m`               | 把每个 rpc 方法的 logic 拆成单独文件，便于维护         |

```go
// Login 处理用户登录
//
// 业务流程与单体版完全一致：
// 1. 按用户名查询用户（不存在 → 错误）
// 2. 校验账号状态（禁用 → 错误）
// 3. bcrypt 校验密码
// 4. 生成 JWT 取 Token
// 5. 查询用户角色 + 菜单
// 6. 异步记录登录日志
// 7. 返回 LoginResp
func (l *LoginLogic) Login(in *sys.LoginReq) (*sys.LoginResp, error) {
    // 1. 查用户     user, err := l.svcCtx.SysUserModel.FindOneByUsername(l.ctx, in.Username)
    if err != nil {
        if err == sysmodel.ErrNotFound {
            l.recordLoginLog(in.Username, 0, in.ClientIp, in.UserAgent, 0, "用户名或密码错误")
            return nil, xerr.NewCodeError(xerr.ErrPasswordWrong)
        }
        l.Errorf("查询用户失败: %v", err)
        return nil, xerr.NewCodeError(xerr.ErrInternal)
    }

    // 2. 状态     if user.Status != 1 {
        l.recordLoginLog(in.Username, user.Id, in.ClientIp, in.UserAgent, 0, "账号已被禁用")
        return nil, xerr.NewCodeError(xerr.ErrAccountDisabled)
    }

    // 3. 密码
    if !encrypt.CheckPassword(in.Password, user.Password) {
        l.recordLoginLog(in.Username, user.Id, in.ClientIp, in.UserAgent, 0, "密码错误")
        return nil, xerr.NewCodeError(xerr.ErrPasswordWrong)
    }

    // 4. Token
    accessToken, err := jwtx.GenerateToken(user.Id, user.Username,
        l.svcCtx.Config.Auth.AccessSecret, l.svcCtx.Config.Auth.AccessExpire)
    if err != nil {
        return nil, xerr.NewCodeError(xerr.ErrInternal)
    }
    refreshToken, err := jwtx.GenerateRefreshToken(user.Id, user.Username,
        l.svcCtx.Config.Auth.AccessSecret, l.svcCtx.Config.Auth.RefreshExpire)
    if err != nil {
        return nil, xerr.NewCodeError(xerr.ErrInternal)
    }

    // 5. 角色 + 菜单（业务逻辑跟单体一模一样，省略，直接复制）
    roleCodes, menuTree := l.loadRolesAndMenus(user.Id)

    // 6. 登录日志
    l.recordLoginLog(in.Username, user.Id, in.ClientIp, in.UserAgent, 1, "登录成功")

    // 7. 组装返回（types.UserInfo 改成 sys.UserInfo）
    return &sys.LoginResp{
        AccessToken:  accessToken,
        RefreshToken: refreshToken,
        ExpiresIn:    l.svcCtx.Config.Auth.AccessExpire,
        UserInfo: &sys.UserInfo{
            UserId:   user.Id,
            Username: user.Username,
            Email:    user.Email,
            Phone:    user.Phone,
            Nickname: user.Nickname,
            Avatar:   user.Avatar,
            Roles:    roleCodes,
            Menus:    menuTree,  // []*sys.MenuItem
```

### 9.2 通用迁移流程（六步法）

每个 RPC 方法严格按这六步执行，能避免 90% 的低级错误：

```
Step 1  解开 sys.proto 中相关 message + service 注释
Step 2  cd service/sys/rpc && goctl rpc protoc pb/sys.proto --go_out=. --go-grpc_out=. --zrpc_out=. -m
Step 3  打开新生成的 internal/logic/{servicename}/{method}_logic.go
Step 4  从原项目 internal/logic/system/{module}/{method}_logic.go 逐行搬业务代码
Step 5  类型替换：types.XxxReq → sys.XxxReq；types.XxxItem → sys.XxxItem；指针字段 *T → 值 + has_xxx
Step 6  go build ./... 通过 → go run sys.go -f etc/sys.yaml 启动 → 进入下个方法
```

#### 9.2.1 类型替换对照表

```
原（HTTP 单体）                                         新（gRPC 微服务）
──────────────────────────────────────────────────────────────────────────────────
go-zero-rpc/internal/types.XxxReq                      go-zero-rpc/sys-rpc/sys.XxxReq
go-zero-rpc/internal/types.XxxResp                     go-zero-rpc/sys-rpc/sys.XxxResp
go-zero-rpc/internal/svc.ServiceContext                go-zero-rpc/sys-rpc/internal/svc.ServiceContext
go-zero-rpc/pkg/xerr                                   go-zero-rpc/common/xerr
go-zero-rpc/pkg/jwtx                                   go-zero-rpc/common/jwtx
go-zero-rpc/pkg/encrypt                                go-zero-rpc/sys-rpc/pkg/encrypt
go-zero-rpc/pkg/casbin                                 go-zero-rpc/sys-rpc/pkg/casbin
go-zero-rpc/internal/common.BuildMenuTree              go-zero-rpc/sys-rpc/internal/common.BuildMenuTree
*int / *string（可选字段）                              int64 + bool has_xxx（proto3 风格）
                                                       或 optional int64 xxx（生成 *int64，需 protoc >= 3.15）
*types.UserItem 单值返回                                单值就是 *sys.UserItem，集合是 []*sys.UserItem

```

#### 9.2.2 错误返回的统一约定

sys-rpc 的 logic 返回 `xerr.NewCodeError(...)`，经 go-zero zrpc 自动包装成 gRPC `status.Error(codes.Code(int(xerr.code)), xerr.msg)`。gateway 端拿到后用 `status.FromError(err)` 解出 code 与 msg，再转成 `response.Fail(...)`。具体实现见 10.5 节。

**logic 内部不要直接 `return errors.New("xxx")`**——要么用 `xerr.NewCodeError(xerr.ErrInternal)`，要么用 `xerr.NewCodeErrorMsg(xerr.ErrParamInvalid, "具体原因")`，否则 gateway 拿不到业务码。

#### 9.2.3 操作日志参数的承接方式

原项目的 `update_user_logic.go` 等很多方法**没有显式接收 operatorId**——单体里通过 ctx 直接拿。RPC 跨进程后必须显式传：在每个写操作的 message 里加 `int64 operator_id = 20;`（按 proto 内 message 现有命名规范，使用 snake_case）。gateway handler 把 `middleware.GetUserIdFromCtx(ctx)` 取到的值塞进去。

```protobuf
message CreateUserReq {
  string username    = 1;
  string password    = 2;
  // ... 其他业务字段
  int64  operator_id = 20;   // 操作人 user_id，由 gateway 注入
}
```

字段编号 20 留给 operator_id，避免业务字段递增时撞号。

### 9.3 sys.go main 注册多个 server

**这一步 9.4 之前就要做**——后续每补一个 service，main 文件都要追加注册一次。打开 `service/sys/rpc/sys.go`，按下面模板改：

```go
package main

import (
    "flag"
    "fmt"

    "go-zero-rpc/sys-rpc/internal/config"
    authsvr "go-zero-rpc/sys-rpc/internal/server/authservice"
    permsvr "go-zero-rpc/sys-rpc/internal/server/permissionservice"
    syssvr "go-zero-rpc/sys-rpc/internal/server/systemservice"
    "go-zero-rpc/sys-rpc/internal/svc"
    "go-zero-rpc/sys-rpc/pb"

    "github.com/zeromicro/go-zero/core/conf"
    "github.com/zeromicro/go-zero/core/service"
    "github.com/zeromicro/go-zero/zrpc"
    "google.golang.org/grpc"
    "google.golang.org/grpc/reflection"
)

var configFile = flag.String("f", "etc/sys.yaml", "the config file")

func main() {
    flag.Parse()

    var c config.Config
    conf.MustLoad(*configFile, &c)
    ctx := svc.NewServiceContext(c)

    s := zrpc.MustNewServer(c.RpcServerConf, func(grpcServer *grpc.Server) {
        sys.RegisterAuthServiceServer(grpcServer, authsvr.NewAuthServiceServer(ctx))
        sys.RegisterSystemServiceServer(grpcServer, syssvr.NewSystemServiceServer(ctx))
        sys.RegisterPermissionServiceServer(grpcServer, permsvr.NewPermissionServiceServer(ctx))

        if c.Mode == service.DevMode || c.Mode == service.TestMode {
            reflection.Register(grpcServer)
        }
    })
    defer s.Stop()

    fmt.Printf("Starting rpc server at %s...\n", c.ListenOn)
    s.Start()
}
```

**关键点**：

1. 三个 service **共用一个 grpc.Server**、**共用一个 zrpc 监听端口**（9100）、**共用一个 ServiceContext**——本质上还是一个进程，只是把方法按业务域分了三个接口契约。
2. 每解开一个 service 注释 → 重新 `goctl rpc protoc` 生成 → main 里追加一行 `RegisterXxxServer`。如果某个 service 还没启用就先注释掉对应行，否则会编译失败。
3. `reflection.Register` 是为了让 grpcurl / postman 能在开发模式下做反射调用，生产模式不开。

`internal/logic/systemservice/list_user_logic.go`：

```go
package systemservice

import (
    "context"

    "go-zero-rpc/common/xerr"
    "go-zero-rpc/sys-rpc/internal/svc"
    "go-zero-rpc/sys-rpc/pb"

    "github.com/zeromicro/go-zero/core/logx"
)

type ListUserLogic struct {
    ctx    context.Context
    svcCtx *svc.ServiceContext
    logx.Logger
}

func NewListUserLogic(ctx context.Context, svcCtx *svc.ServiceContext) *ListUserLogic {
    return &ListUserLogic{ctx: ctx, svcCtx: svcCtx, Logger: logx.WithContext(ctx)}
}

// ListUser 分页查询用户列表（含角色 code 拼装）
//
// 业务流程与单体版 internal/logic/system/user/list_user_logic.go 完全一致：
// 1. 分页查询 sys_user
// 2. 批量查 sys_user_role 拿 user_id -> []role_id
// 3. 批量查 sys_role 拿 role_id -> code
// 4. 拼接 user_id -> []code，组装 UserItem
func (l *ListUserLogic) ListUser(in *sys.ListUserReq) (*sys.ListUserResp, error) {
    var statusPtr *int
    if in.HasStatus {
        v := int(in.Status)
        statusPtr = &v
    }

    users, total, err := l.svcCtx.SysUserModel.List(l.ctx, int(in.Page), int(in.PageSize), in.Keyword, statusPtr)
    if err != nil {
        l.Errorf("查询用户列表失败：%v", err)
        return nil, xerr.NewCodeError(xerr.ErrInternal)
    }

    userIds := make([]int64, 0, len(users))
    for _, u := range users {
        userIds = append(userIds, u.Id)
    }
    userRoleIds, err := l.svcCtx.SysUserRoleModel.GetRoleIdsByUserIds(l.ctx, userIds)
    if err != nil {
        l.Errorf("批量查询用户关联角色失败：%v", err)
        return nil, xerr.NewCodeError(xerr.ErrInternal)
    }

    roleIdSet := make(map[int64]struct{})
    for _, ur := range userRoleIds {
        roleIdSet[ur.RoleId] = struct{}{}
    }
    roleIds := make([]int64, 0, len(roleIdSet))
    for id := range roleIdSet {
        roleIds = append(roleIds, id)
    }

    roleMap := make(map[int64]string)
    if len(roleIds) > 0 {
        roles, err := l.svcCtx.SysRoleModel.FindByIds(l.ctx, roleIds)
        if err != nil {
            l.Errorf("批量查询角色信息失败：%v", err)
            return nil, xerr.NewCodeError(xerr.ErrInternal)
        }
        for _, r := range roles {
            roleMap[r.Id] = r.Code
        }
    }

    userRoleMap := make(map[int64][]string)
    for _, ur := range userRoleIds {
        if code, ok := roleMap[ur.RoleId]; ok {
            userRoleMap[ur.UserId] = append(userRoleMap[ur.UserId], code)
        }
    }

    list := make([]*sys.UserItem, 0, len(users))
    for _, u := range users {
        list = append(list, &sys.UserItem{
            Id:        u.Id,
            Username:  u.Username,
            Nickname:  u.Nickname,
            Email:     u.Email,
            Phone:     u.Phone,
            Avatar:    u.Avatar,
            Status:    u.Status,
            Remark:    u.Remark,
            Roles:     userRoleMap[u.Id],
            CreatedAt: u.CreatedAt.Format("2006-01-02 15:04:05"),
            UpdatedAt: u.UpdatedAt.Format("2006-01-02 15:04:05"),
        })
    }
    return &sys.ListUserResp{Total: total, List: list}, nil
}
```

#### 9.4.4 UpdateUser（演示 has_xxx 处理可选字段）

```go
func (l *UpdateUserLogic) UpdateUser(in *sys.UpdateUserReq) (*sys.CommonResp, error) {
    sysUser, err := l.svcCtx.SysUserModel.FindOne(l.ctx, in.Id)
    if err != nil {
        if err == sqlx.ErrNotFound {
            return nil, xerr.NewCodeError(xerr.ErrUserNotFound)
        }
        l.Errorf("查询用户[%d]失败：%v", in.Id, err)
        return nil, xerr.NewCodeError(xerr.ErrInternal)
    }
    if sysUser.DeletedAt.Valid {
        return nil, xerr.NewCodeError(xerr.ErrParamInvalid)
    }

    // has_xxx 用来区分"传了空值"和"没传"——这是 proto3 不支持指针的等价方案
    updates := make(map[string]interface{})
    if in.HasNickname { updates["nickname"] = in.Nickname }
    if in.HasEmail    { updates["email"]    = in.Email    }
    if in.HasPhone    { updates["phone"]    = in.Phone    }
    if in.HasAvatar   { updates["avatar"]   = in.Avatar   }
    if in.HasStatus   { updates["status"]   = in.Status   }
    if in.HasRemark   { updates["remark"]   = in.Remark   }

    needUpdateRoles := in.HasRoleIds
    if len(updates) == 0 && !needUpdateRoles {
        return nil, xerr.NewCodeErrorMsg(xerr.ErrParamInvalid, "更新字段为空")
    }

    if needUpdateRoles && len(in.RoleIds) > 0 {
        roles, err := l.svcCtx.SysRoleModel.FindByIds(l.ctx, in.RoleIds)
        if err != nil {
            return nil, xerr.NewCodeError(xerr.ErrInternal)
        }
        if len(roles) != len(in.RoleIds) {
            return nil, xerr.NewCodeError(xerr.ErrRoleNotFound)
        }
    }

    err = l.svcCtx.Orm.WithContext(l.ctx).Transaction(func(tx *gorm.DB) error {
        if len(updates) > 0 {
            if err := l.svcCtx.SysUserModel.UpdateTrans(l.ctx, tx, in.Id, updates); err != nil {
                return xerr.NewCodeError(xerr.ErrInternal)
            }
        }
        if needUpdateRoles {
            if err := l.svcCtx.SysUserRoleModel.AssignRolesTrans(l.ctx, tx, in.Id, in.RoleIds); err != nil {
                return xerr.NewCodeError(xerr.ErrInternal)
            }
        }
        return nil
    })
    if err != nil {
        return nil, err
    }
    return &sys.CommonResp{Code: 0, Msg: "ok"}, nil
}
```

```go
package common

import (
    sysmodel "go-zero-rpc/sys-rpc/internal/model"
    "go-zero-rpc/sys-rpc/pb"
)

func BuildMenuTree(menus []sysmodel.SysMenu) []*sys.MenuItem {
    nodeMap := make(map[int64]*sys.MenuItem, len(menus))
    for _, m := range menus {
        nodeMap[m.Id] = &sys.MenuItem{
            Id: m.Id, ParentId: m.ParentId,
            MenuName: m.MenuName, MenuType: m.MenuType,
            Path: m.Path, Component: m.Component, Icon: m.Icon,
            Sort: m.Sort, Perms: m.Perms, Status: m.Status,
        }
    }
    roots := make([]*sys.MenuItem, 0)
    for _, m := range menus {
        node := nodeMap[m.Id]
        if m.ParentId == 0 {
            roots = append(roots, node)
            continue
        }
        if parent, ok := nodeMap[m.ParentId]; ok {
            parent.Children = append(parent.Children, node)
        }
    }
    return roots
}
```

```go
package permissionservice

import (
    "context"

    "go-zero-rpc/sys-rpc/internal/svc"
    "go-zero-rpc/sys-rpc/pb"

    "github.com/zeromicro/go-zero/core/logx"
)

type CheckPermissionLogic struct {
    ctx    context.Context
    svcCtx *svc.ServiceContext
    logx.Logger
}

func NewCheckPermissionLogic(ctx context.Context, svcCtx *svc.ServiceContext) *CheckPermissionLogic {
    return &CheckPermissionLogic{ctx: ctx, svcCtx: svcCtx, Logger: logx.WithContext(ctx)}
}

// CheckPermission 把单体版 CasbinMiddleware 的核心逻辑整体搬到这里
func (l *CheckPermissionLogic) CheckPermission(in *sys.CheckPermissionReq) (*sys.CheckPermissionResp, error) {
    if in.UserId == 0 {
        return &sys.CheckPermissionResp{Allowed: false, Reason: "未登录"}, nil
    }

    roleIds, err := l.svcCtx.SysUserRoleModel.GetRoleIdsByUserId(l.ctx, in.UserId)
    if err != nil {
        l.Errorf("查询用户[%d]角色失败：%v", in.UserId, err)
        return &sys.CheckPermissionResp{Allowed: false, Reason: "查询角色失败"}, nil
    }
    if len(roleIds) == 0 {
        return &sys.CheckPermissionResp{Allowed: false, Reason: "用户无角色"}, nil
    }

    for _, rid := range roleIds {
        role, err := l.svcCtx.SysRoleModel.FindOneByRoleId(l.ctx, rid)
        if err != nil || role == nil {
            continue
        }
        ok, err := l.svcCtx.Enforcer.Enforce(role.Code, in.Path, in.Method)
        if err != nil {
            l.Errorf("Casbin Enforce 失败：%v", err)
            continue
        }
        if ok {
            return &sys.CheckPermissionResp{Allowed: true}, nil
        }
    }
    return &sys.CheckPermissionResp{Allowed: false, Reason: "无权限"}, nil
}
```

> 这里**不要再 `response.FailForbidden(w, r)`**——RPC 层不感知 HTTP 响应。是否拒绝由 gateway 端中间件根据 `Allowed` 字段决定。

### 10.5 ServiceContext：一个 zrpc 连接，三个 client

**核心纪律**：分组方案下 gateway 只 `zrpc.MustNewClient` **一次**，三个 client wrapper 复用同一个底层连接。

`gateway/internal/svc/service_context.go`：

```go
package svc

import (
    "go-zero-rpc/gateway/internal/config"
    "go-zero-rpc/gateway/internal/middleware"
    authclient "go-zero-rpc/sys-rpc/client/authservice"
    permclient "go-zero-rpc/sys-rpc/client/permissionservice"
    sysclient  "go-zero-rpc/sys-rpc/client/systemservice"

    "github.com/zeromicro/go-zero/rest"
    "github.com/zeromicro/go-zero/zrpc"
)

type ServiceContext struct {
    Config config.Config

    AuthRpc       authclient.AuthService
    SystemRpc     sysclient.SystemService
    PermissionRpc permclient.PermissionService

    AuthMiddleware    rest.Middleware
    CasbinMiddleware  rest.Middleware
    OperLogMiddleware rest.Middleware
}

func NewServiceContext(c config.Config) *ServiceContext {
    cli := zrpc.MustNewClient(c.SysRpc) // 只建一次，下面三个 client 共用底层 conn

    permRpc := permclient.NewPermissionService(cli)

    return &ServiceContext{
        Config:        c,
        AuthRpc:       authclient.NewAuthService(cli),
        SystemRpc:     sysclient.NewSystemService(cli),
        PermissionRpc: permRpc,

        AuthMiddleware:    middleware.NewAuthMiddleware(c).Handle,
        CasbinMiddleware:  middleware.NewCasbinMiddleware(permRpc).Handle,
        OperLogMiddleware: middleware.NewOperLogMiddleware(sysclient.NewSystemService(cli)).Handle,
    }
}
```

> **为什么不用 `c.PermRpc`、`c.SystemRpc` 三段配置？** 因为三个 service 在同一个 grpc 进程上同一个端口，etcd key 也是同一个 `sys.rpc`。只需一个 `SysRpc` 配置就够了。

```go
    "context"

    "go-zero-rpc/gateway/internal/svc"
    "go-zero-rpc/gateway/internal/types"
    "go-zero-rpc/sys-rpc/pb"

    "github.com/zeromicro/go-zero/core/logx"

type ListUserLogic struct {
    ctx    context.Context
    svcCtx *svc.ServiceContext
    logx.Logger
}

func NewListUserLogic(ctx context.Context, svcCtx *svc.ServiceContext) *ListUserLogic {
    return &ListUserLogic{ctx: ctx, svcCtx: svcCtx, Logger: logx.WithContext(ctx)}
}

// ListUser 把 HTTP 请求转换成 RPC 调用，并把 RPC 响应转换回 HTTP DTO
func (l *ListUserLogic) ListUser(req *types.ListUserReq) (*types.ListUserResp, error) {
    rpcReq := &sys.ListUserReq{
        Page:     int64(req.Page),

            Username:  u.Username,
            Nickname:  u.Nickname,

            Avatar:    u.Avatar,
```

### 10.7 类型转换的工程化建议

每个模块都要写 N 个 `convertXxx` 转换函数，内容机械重复。三种应对策略：

| 策略 | 工时 | 维护成本 | 推荐度 |
|---|---|---|---|
| **手写**（推荐） | 6-8h | 低（每个字段显式可见，便于排查） | ★★★★★ |
| 用 [`copier`](https://github.com/jinzhu/copier) 反射拷贝 | 2h | 中（字段名不一致时易出错，反射性能差） | ★★ |
| 写 protoc 插件自动生成 | 高 | 极低 | 第一次改造不推荐 |

**手写最快最稳**——proto 字段（snake_case → CamelCase）和 .api 字段（已经是 PascalCase）大多数能一一对应，IDE 用 `Alt+Enter → Generate Field Mapping` 也能半自动。

### 10.8 错误传递：gRPC status → HTTP response

sys-rpc logic 返回 `xerr.NewCodeError(xerr.ErrPasswordWrong)`，go-zero zrpc 自动用 `status.Error(codes.Code(xerr.code), xerr.msg)` 包装。gateway 端要解出来转成原项目格式的 JSON 响应。

`gateway/internal/handler/responseutil.go`（新建）：

```go
package handler

import (
    "errors"
    "net/http"

    "go-zero-rpc/common/xerr"
    "go-zero-rpc/gateway/pkg/response"

    "github.com/zeromicro/go-zero/core/logx"
    "github.com/zeromicro/go-zero/rest/httpx"
    "google.golang.org/grpc/status"
)

// HandleResponse 统一处理 RPC/业务返回，确保前端始终拿到原项目的 {code,msg,data} 格式
func HandleResponse(w http.ResponseWriter, r *http.Request, data any, err error) {
    if err == nil {
        response.OkData(w, r, data)
        return
    }

    // 1. 优先识别 gRPC status 错误
    if st, ok := status.FromError(err); ok {
        code := int32(st.Code())
        if code == 0 {
            code = response.CodeInternal
        }
        response.Fail(w, r, code, st.Message())
        return
    }

    // 2. 识别本地 xerr.CodeError
    var ce *xerr.CodeError
    if errors.As(err, &ce) {
        response.Fail(w, r, int32(ce.Code), ce.Msg)
        return
    }

    // 3. 兜底
    logx.WithContext(r.Context()).Errorf("未识别错误：%v", err)
    response.FailInternal(w, r)
    httpx.ErrorCtx(r.Context(), w, err)
}
```

把所有 handler 末尾的 `httpx.ErrorCtx / httpx.OkJsonCtx` 替换为 `handler.HandleResponse`。

### 11.2 CasbinMiddleware：改造为远程鉴权

#### 11.2.1 与原版的差别

| 维度 | 原版（单体） | 新版（gateway） |
|---|---|---|
| 依赖 | `*casbinv2.Enforcer` + `sqlx.SqlConn` + `*gorm.DB` | `permclient.PermissionService`（一个 RPC client） |
| 数据库连接 | 直连 sys_user_role / sys_role | 不直连任何数据库 |
| Enforce 调用 | 本地内存 | 通过 RPC |
| 结构体大小 | 大（持有所有依赖） | 小（一个 client 接口） |

#### 11.2.2 实现

`gateway/internal/middleware/casbin_middleware.go`：

```go
package middleware

import (
    "net/http"

    "go-zero-rpc/gateway/pkg/response"
    permclient "go-zero-rpc/sys-rpc/client/permissionservice"
    "go-zero-rpc/sys-rpc/pb"

    "github.com/zeromicro/go-zero/core/logx"
)

// CasbinMiddleware 通过 PermissionService.CheckPermission 远程鉴权。
//
// 与单体版相比：
// 1. 不再直连 sys_user_role / sys_role 表
// 2. 鉴权逻辑全部在 sys-rpc 端，gateway 只负责传 path/method/userId
// 3. RPC 调用失败一律视为 403（保守拒绝），避免被错误放行
type CasbinMiddleware struct {
    permRpc permclient.PermissionService
}

func NewCasbinMiddleware(permRpc permclient.PermissionService) *CasbinMiddleware {
    return &CasbinMiddleware{permRpc: permRpc}
}

func (m *CasbinMiddleware) Handle(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        userId := GetUserIdFromCtx(r.Context())
        if userId == 0 {
            response.FailUnauthorized(w, r)
            return
        }

        resp, err := m.permRpc.CheckPermission(r.Context(), &sys.CheckPermissionReq{
            UserId: userId,
            Path:   r.URL.Path,
            Method: r.Method,
        })
        if err != nil {
            logx.WithContext(r.Context()).Errorf(
                "CheckPermission RPC 调用失败 user=%d path=%s method=%s err=%v",
                userId, r.URL.Path, r.Method, err,
            )
            response.FailForbidden(w, r)
            return
        }
        if !resp.Allowed {
            logx.WithContext(r.Context()).Infof(
                "鉴权拒绝 user=%d path=%s method=%s reason=%s",
                userId, r.URL.Path, r.Method, resp.Reason,
            )
            response.FailForbidden(w, r)
            return
        }

        next.ServeHTTP(w, r)
    }
}
```

### 11.3 性能权衡

每个被 CasbinMiddleware 保护的请求都增加一次 RPC 往返（约 1-3ms 局域网内）。30 + 个被鉴权接口意味着每个请求至少 1 跳 RPC 开销。

**改造期不要做以下优化**——先跑通整链路。后续如果出现性能问题，按下面的顺序加：

1. **gateway 本地 LRU 缓存**：key = `userId|path|method`，value = `bool`，TTL 30s。失效策略：用户角色变更时主动清理。
2. **gRPC 连接保活与流式**：CheckPermission 高频时把 TCP keepalive 调短，避免冷启动的 TCP 三次握手。
3. **Casbin 副本同步**：gateway 端持有一个只读 Enforcer，sys-rpc 通过 etcd 发布"角色权限变更"事件，gateway 订阅并增量更新本地策略。这是最复杂但最快的方案。

## 第 12 章  里程碑 8：操作日志的迁移（最容易踩坑的一步）

> **本章前置**
>
> - 原 `internal/middleware/operlogmiddleware.go` 在 HTTP 层包装 ResponseWriter、缓存 Body、异步落库
> - 单体版直接 `operLogModel.Insert(...)`，gateway 不能再这么写——它没有 sys_oper_log 表的访问权
>
> **本章目标**：把"日志采集"留在 gateway，"日志落库"拆给 sys-rpc，二者通过 `WriteOperLog` RPC 异步衔接。

---

### 12.1 设计要点

```
浏览器 ──HTTP──▶ gateway OperLogMiddleware
                ├─ wrap ResponseWriter，捕获响应体
                ├─ 缓存 Body（注意：要重新塞回 r.Body 给后续 handler）
                ├─ next.ServeHTTP(...)
                ├─ 计算耗时、解析状态码
                └─ 异步 goroutine：
                       └─ AuthRpc/SysRpc.WriteOperLog(...)  ──RPC──▶ sys-rpc
                                                                        └─ Insert sys_oper_log
```

**关键工程原则**：
1. 写日志走异步——主链路不阻塞
2. 异步不能 `r.Context()` 直接复用（请求结束后 ctx 会被 cancel）→ 用 `context.Background()` + 自己的超时控制
3. 异步要带 panic recover——日志写库失败不能影响主请求

### 12.2 sys.proto 新增 WriteOperLog

### 12.3 sys-rpc 端 WriteOperLog 实现

```go
package systemservice

import (
    "context"
    "database/sql"
    "time"

    sysmodel "go-zero-rpc/sys-rpc/internal/model"
    "go-zero-rpc/sys-rpc/internal/svc"
    "go-zero-rpc/sys-rpc/pb"

    "github.com/zeromicro/go-zero/core/logx"

type WriteOperLogLogic struct {
    ctx    context.Context
    svcCtx *svc.ServiceContext
    logx.Logger
}

func NewWriteOperLogLogic(ctx context.Context, svcCtx *svc.ServiceContext) *WriteOperLogLogic {
    return &WriteOperLogLogic{ctx: ctx, svcCtx: svcCtx, Logger: logx.WithContext(ctx)}
}

func (l *WriteOperLogLogic) WriteOperLog(in *sys.WriteOperLogReq) (*sys.CommonResp, error) {
    log := &sysmodel.SysOperLog{
        Title:         in.Title,
        BusinessType:  in.BusinessType,
        Method:        in.Method,
        RequestMethod: in.ReqMethod,
        OperatorType:  1, // 1=后台用户
        OperatorId:    in.OperatorId,
        OperatorName:  in.OperatorName,
        DeptName:      in.DeptName,
        OperUrl:       in.ReqUrl,
        OperIp:        in.Ip,
        OperParam:     toNullString(in.ReqParam),
        JsonResult:    toNullString(in.RespResult),
        Status:        in.Status,
        ErrorMsg:      toNullString(in.ErrorMsg),
        CostTimeMs:    in.CostMs,
        OperTime:      time.Now(),
    }
    if _, err := l.svcCtx.SysOperLogModel.Insert(l.ctx, log); err != nil {
        l.Errorf("写操作日志失败：%v", err)
        // 不向调用方报错——操作日志不是关键路径
    }
    return &sys.CommonResp{Code: 0, Msg: "ok"}, nil
}

func toNullString(s string) sql.NullString {
    if s == "" {
        return sql.NullString{Valid: false}
    }
    return sql.NullString{String: s, Valid: true}
}
```

### 12.4 gateway 端 OperLogMiddleware

`gateway/internal/middleware/operlog_middleware.go`：

```go
package middleware

import (
    "bytes"
    "context"
    "io"
    "net/http"
    "strings"
    "time"

    sysclient "go-zero-rpc/sys-rpc/client/systemservice"
    "go-zero-rpc/sys-rpc/pb"

    "github.com/zeromicro/go-zero/core/logx"
)

const (
    maxBodyBytes  = 2048 // 入参/响应截断长度
    asyncTimeout  = 3 * time.Second
)

type OperLogMiddleware struct {
    rpc sysclient.SystemService
}

func NewOperLogMiddleware(rpc sysclient.SystemService) *OperLogMiddleware {
    return &OperLogMiddleware{rpc: rpc}
}

func (m *OperLogMiddleware) Handle(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()

        // 1. 缓存 request body（必须重新塞回，否则后续 handler 读不到）
        var reqParam string
        if r.Body != nil && r.Method != http.MethodGet {
            body, err := io.ReadAll(io.LimitReader(r.Body, maxBodyBytes))
            if err == nil {
                reqParam = string(body)
                r.Body = io.NopCloser(bytes.NewBuffer(body))
            }
        }

        // 2. 包装 ResponseWriter 截响应
        rw := &respWriter{ResponseWriter: w, body: &bytes.Buffer{}, status: http.StatusOK}

        // 3. 调用业务
        next.ServeHTTP(rw, r)

        // 4. 异步写日志（不阻塞响应）
        userId := GetUserIdFromCtx(r.Context())
        username := GetUsernameFromCtx(r.Context())
        ip := GetClientIP(r)
        respBody := truncate(rw.body.String(), maxBodyBytes)

        operStatus := int64(1)
        if rw.status >= 400 {
            operStatus = 0
        }

        go func() {
            defer func() {
                if v := recover(); v != nil {
                    logx.Errorf("OperLogMiddleware panic: %v", v)
                }
            }()
            ctx, cancel := context.WithTimeout(context.Background(), asyncTimeout)
            defer cancel()
            _, _ = m.rpc.WriteOperLog(ctx, &sys.WriteOperLogReq{
                Title:        getOperTitle(r.URL.Path),
                BusinessType: getBusinessType(r.Method),
                Method:       r.URL.Path,
                ReqMethod:    r.Method,
                OperatorId:   userId,
                OperatorName: username,
                ReqUrl:       r.URL.Path,
                ReqParam:     reqParam,
                RespResult:   respBody,
                Status:       operStatus,
                Ip:           ip,
                CostMs:       time.Since(start).Milliseconds(),
            })
        }()
    }
}

type respWriter struct {
    http.ResponseWriter
    body   *bytes.Buffer
    status int
}

func (r *respWriter) WriteHeader(s int)             { r.status = s; r.ResponseWriter.WriteHeader(s) }
func (r *respWriter) Write(b []byte) (int, error)   { r.body.Write(b); return r.ResponseWriter.Write(b) }

func truncate(s string, n int) string {
    if len(s) <= n {
        return s
    }
    return s[:n] + "...(truncated)"
}

func getBusinessType(method string) int64 {
    switch strings.ToUpper(method) {
    case http.MethodPost:                    return 1
    case http.MethodPut, http.MethodPatch:   return 2
    case http.MethodDelete:                  return 3
    case http.MethodGet:                     return 4
    default:                                 return 0
    }
}

func getOperTitle(path string) string {
    parts := strings.Split(strings.Trim(path, "/"), "/")
    switch len(parts) {
    case 0, 1:
        return path
    case 2:
        return parts[1]
    default:
        return parts[1] + "/" + parts[2]
    }
}
```

> `GetUserIdFromCtx`、`GetUsernameFromCtx`、`GetClientIP` 复用 11.1 节里 AuthMiddleware 提供的工具函数。

### 12.6 为什么不用 gRPC interceptor 在 sys-rpc 端捕获

直觉上"日志属于服务端，应该在 RPC 端拦截"，但现实场景下不可行：

| 项 | gateway 中间件 | sys-rpc gRPC interceptor |
|---|---|---|
| HTTP method（GET/POST） | 有 | 无（已变成 method 名 ListUser） |
| 原始 URL（含 query） | 有 | 无 |
| User-Agent | 有 | 无（除非显式塞 metadata） |
| Client IP | 有 | 无 |
| 响应 HTTP status | 有 | 无（gRPC 只有 status code） |
| 操作人姓名 | 已查过/可从 ctx 拿 | 需要再查一次 |

**结论**：日志采集必须在 gateway 完成，sys-rpc 只负责写库。

### 12.7 第 12 章 总验证

1. 调一个写接口（如 PUT /api/system/user/1）
2. SQL 查 `select * from sys_oper_log order by id desc limit 1`
3. 期望字段：`title=system/user`、`business_type=2`、`oper_url=/api/system/user/1`、`oper_param=...`、`status=1`、`cost_time_ms`>0
4. **故意触发失败**：传一个不存在的 user_id → status=0，error_msg 含错误信息
5. 关闭 sys-rpc，再调写接口 → 业务接口仍能返回（异步写日志失败不影响主链路），日志有 `OperLogMiddleware panic` 或 RPC timeout warning

`git commit -m "feat(gateway,sys-rpc): 操作日志通过 RPC 异步落库"`。

### 13.1 为什么不能让二进制走 gRPC

```
浏览器 multipart/form-data ──▶ gateway 解析文件流 ──▶ ?? ──▶ sys-rpc Insert
                                                  ▲
                                                  此处如何传？
```

把整个文件 base64 进 gRPC message 有三个致命问题：

1. **gRPC 默认 4MB message 上限**——超过即报 `RESOURCE_EXHAUSTED`
2. **内存膨胀**：base64 编码 ×1.33；gateway + sys-rpc 两端都需要分配 buffer
3. **多一跳网络**：浪费带宽和时间

### 13.2 推荐方案：gateway 直接落盘 + RPC 写元数据

```
浏览器 multipart/form-data
     │
     ▼ gateway UploadFileHandler
     ├─ 校验扩展名、Content-Length
     ├─ 落盘到 gateway 本地（或 OSS / MinIO / NFS）
     ├─ 调 sys-rpc.RegisterFile(fileName, fileUrl, fileSize, mimeType, uploaderId)
     └─ 返回 {fileId, fileUrl} 给前端
```

**前提**：gateway 与 sys-rpc 必须能访问同一份存储。三种工程选项：

| 选项 | 说明 | 适用场景 |
|---|---|---|
| 本地磁盘 + 静态资源服务器 | gateway 落盘到本机 `uploads/`，nginx/gateway 自身做 `/static/*` 路由 | 单实例部署 |
| NFS / 共享卷 | 多个 gateway 实例挂载同一目录 | 多副本但同物理机房 |
| **OSS / MinIO**（推荐） | gateway 直接 PutObject 到对象存储，URL 全平台可访问 | 任何生产环境 |

### 13.4 UploadFileHandler 实现

`gateway/internal/handler/system/file/upload_file_handler.go`：

```go
package file

import (
    "fmt"
    "net/http"
    "path/filepath"
    "strings"

    "go-zero-rpc/gateway/internal/middleware"
    "go-zero-rpc/gateway/internal/svc"
    "go-zero-rpc/gateway/pkg/response"
    "go-zero-rpc/gateway/pkg/upload"
    "go-zero-rpc/sys-rpc/pb"
)

func UploadFileHandler(svcCtx *svc.ServiceContext) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        // 1. 校验大小（注意 r.Body 由 ParseMultipartForm 间接读）
        if err := r.ParseMultipartForm(svcCtx.Config.Upload.MaxSize); err != nil {
            response.Fail(w, r, response.CodeParamInvalid, "文件大小超限或表单解析失败")
            return
        }
        file, header, err := r.FormFile("file")
        if err != nil {
            response.Fail(w, r, response.CodeParamInvalid, "缺少 file 字段")
            return
        }
        defer file.Close()

        // 2. 校验扩展名
        ext := strings.ToLower(filepath.Ext(header.Filename))
        if !contains(svcCtx.Config.Upload.AllowedExts, ext) {
            response.Fail(w, r, response.CodeParamInvalid, fmt.Sprintf("不支持的文件类型：%s", ext))
            return
        }

        // 3. 落盘（upload.Save 内部应做"防路径穿越 + 唯一文件名"）
        fileName, fileUrl, err := upload.Save(svcCtx.Config.Upload.Path, file, header)
        if err != nil {
            response.FailInternal(w, r)
            return
        }

        // 4. 调 RPC 写元数据
        userId := middleware.GetUserIdFromCtx(r.Context())
        rpcResp, err := svcCtx.SystemRpc.RegisterFile(r.Context(), &sys.RegisterFileReq{
            FileName:   fileName,
            FileUrl:    fileUrl,
            FileSize:   header.Size,
            MimeType:   header.Header.Get("Content-Type"),
            UploaderId: userId,
        })
        if err != nil {
            // 元数据写库失败时，可选：删除已落盘文件做补偿
            _ = upload.Remove(svcCtx.Config.Upload.Path, fileName)
            response.FailInternal(w, r)
            return
        }

        response.OkData(w, r, map[string]any{
            "fileId":  rpcResp.FileId,
            "fileUrl": fileUrl,
        })
    }
}

func contains(list []string, s string) bool {
    for _, v := range list {
        if v == s {
            return true
        }
    }
    return false
}
```

## 第 16 章  常见坑与排查方法

### 16.1 sys-rpc 启动了但 gateway 连不上

**现象**：gateway 启动报 `rpc dial fail` 或 `etcd resolver: no available endpoint`。

**排查**：

1. `docker exec etcd-dev etcdctl get --prefix sys.rpc` 看 sys-rpc 是否注册成功
2. 检查 `sys.yaml` 的 `Etcd.Key` 和 `gateway.yaml` 的 `SysRpc.Etcd.Key` 是否完全一致（区分大小写）
3. 检查 sys-rpc 的 `ListenOn` 是 `0.0.0.0:9100`，**不是** `127.0.0.1:9100`（127.0.0.1 在容器场景下别的容器连不上）
4. gateway 与 sys-rpc 不在同一台机器：检查防火墙、安全组

### 16.2 proto 改了但生成代码没更新

`goctl rpc protoc` 默认不会覆盖已有的 logic 文件（你填过的业务代码）。如果你改了 LoginReq 的字段：

- `sys/sys.pb.go` 自动更新（无条件覆盖）
- `internal/logic/.../login_logic.go` 不动

你的 logic 可能编译失败（引用了被删字段）——这是**正常**的，按编译错误改即可。

如果想强制覆盖某个 logic，删掉对应文件再生成；但**先 commit 现有代码再删**。

### 16.3 proto3 可选字段（optional）的两种方案

原项目大量用 `*string`、`*int` 表示可选字段。proto3 有两种应对：

**方案 A（默认推荐，本指南采用）**：用零值表示"未传"，区分零值与未传时加 `bool has_xxx`：

```protobuf
message UpdateUserReq {
  int64  id            = 1;
  string nickname      = 2;
  bool   has_nickname  = 3;
  int64  status        = 4;
  bool   has_status    = 5;
}
```

业务代码：`if in.HasNickname { update.Nickname = in.Nickname }`。

**方案 B（protoc >= 3.15）**：用 `optional` 关键字：

```protobuf
message UpdateUserReq {
  int64           id       = 1;
  optional string nickname = 2;     // 生成 *string
  optional int64  status   = 3;     // 生成 *int64
}
```

生成的 Go 代码与原项目 `*T` 一致。**优点**：少一个布尔字段。**缺点**：生成代码用法（GetXxx() / nil 判定）与普通字段不一致，团队成员要学。

### 16.4 中文错误消息乱码

gRPC 协议本身用 UTF-8，中文不会乱码。但有两个易踩点：

1. **terminal 编码**：Windows cmd 默认 GBK，看到的"乱码"实际是终端问题，不是数据问题；切到 PowerShell 或 Git Bash 即可
2. **status.Error vs xerr.NewCodeError**：用 `status.Error(codes.Code(xerr.ErrPasswordWrong), "用户名或密码错误")` 包装，gateway 端用 `status.FromError(err)` 解出，详见 10.8

### 16.5 跨进程上下文丢失

`ctx.Value(...)` 不会自动序列化到下游 RPC。改造后必须**显式在 proto Req 里传 userId / clientIp 等**：

```protobuf
message LoginReq {
  string username   = 1;
  string password   = 2;
  string client_ip  = 3;     // gateway 注入
  string user_agent = 4;
}
```

gateway handler 端：

```go
rpcReq := &sys.LoginReq{
    Username:  req.Username,
    Password:  req.Password,
    ClientIp:  middleware.GetClientIP(r),
    UserAgent: r.UserAgent(),
}
```

如果字段太多想统一传，可用 gRPC metadata：

```go
// gateway 注入
md := metadata.Pairs("x-user-id", strconv.FormatInt(userId, 10))
ctx = metadata.NewOutgoingContext(ctx, md)

// sys-rpc 拦截器解出
md, _ := metadata.FromIncomingContext(ctx)
userIdStr := md.Get("x-user-id")[0]
```

但 proto Req 显式字段更直观、可读性更好，**首选 proto 字段**。

### 16.6 数据库连接数爆炸

sys-rpc 自带一个连接池（默认 20 active）。如果其他业务 RPC 也直连 sys_* 表，连接数翻倍。

**解决**：守住边界——**只有 sys-rpc 能访问 sys_* 表**。其他业务想拿用户数据必须走 sys-rpc 的 RPC 接口。这是微服务的纪律。

### 16.7 编译报错：找不到 `go-zero-rpc/sys-rpc/...`

跨模块导入时，如果不用 `go.work`，必须在 gateway 或 plating-rpc 的 go.mod 里加：

```
require go-zero-rpc/sys-rpc v0.0.0
replace go-zero-rpc/sys-rpc => ../service/sys/rpc
```

用 `go.work` 就不需要 `replace`，但 **`go.work` 不应提交到 CI**——CI 部署时必须靠 `go.mod` 的 `replace` 或正式 publish。

### 16.8 多 service 分组带来的特有坑

#### 16.8.1 sys.go 注册顺序错

```go
sys.RegisterAuthServiceServer(grpcServer, ...)
sys.RegisterSystemServiceServer(grpcServer, ...)   // 写一个少一个
sys.RegisterPermissionServiceServer(grpcServer, ...)
```

**少注册一个 service 不会报错**，但 gateway 调它时报 `unknown service`。验证方法：grpcurl + reflection 列服务（见 9.12）。

#### 16.8.2 client/sys/ 与 client/authservice/ 冲突

早期 1.9.2 单 service 生成的产物 `client/sys/`、`internal/logic/sys/`、`internal/server/sys/` 必须删掉（见 9.0.3），否则编译时会因 `package sys` 与生成的 `sys/` package 冲突。

#### 16.8.3 三个 client 共用 conn vs 各开一个

正确做法（见 10.5）：

```go
cli := zrpc.MustNewClient(c.SysRpc)
authRpc := authclient.NewAuthService(cli)
sysRpc  := sysclient.NewSystemService(cli)
permRpc := permclient.NewPermissionService(cli)
```

错误做法：每个 client 单独 `zrpc.MustNewClient(...)` —— gateway 与 sys-rpc 之间会建 3 条 TCP 连接，毫无意义且浪费 fd。

### 16.9 Logout 后 token 仍能用

如果 11.1.4 没实现黑名单：原项目的"Logout 把 token 写 Redis 黑名单 + AuthMiddleware 检查黑名单"机制断了。

**临时方案**：缩短 access token TTL（默认 1200s 改 300s），靠 refresh token 续期 + 服务端 refresh token 黑名单。

**完整方案**：补一个 RPC `IsTokenRevoked(tokenID string) -> bool`，AuthMiddleware 验证完 JWT 再调一次。

### 16.10 操作日志看不到

排查顺序：

1. 路由配置：`@server middleware:` 里没写 `OperLogMiddleware`
2. 异步 goroutine panic：grep gateway 日志 `OperLogMiddleware panic`
3. RPC timeout：12.4 设的 `asyncTimeout = 3s`，sys-rpc 慢时会超时丢日志
4. sys-rpc 端 logic 写库失败：grep sys-rpc 日志 `写操作日志失败`
